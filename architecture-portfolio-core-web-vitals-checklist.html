Core Web Vitals for architecture portfolios: keep the images, lose the delays.

Keep the impact of your renderings and film heroes while improving LCP, INP and CLS on mobile.

By Michal Kašpárek · Architect and visualisation specialist24 November 2026
In this guideBegin with the visitor LCP, INP and CLS Prioritise the hero Manage hero video Prevent layout shifts Make galleries responsive Test page templates Launch checklist

Measure the visitor experience, not just the size of the image.

An architecture studio can have outstanding photography and still lose visitors while they stare at an empty hero, wait for a gallery to appear or try to open a project. Core Web Vitals help separate those delivery problems from the quality of the architecture and the design. The aim is to keep the visual work intact while making the page respond predictably.

Begin with three representative templates: the homepage with its large visual, a project detail containing many photographs and a project index with filters. A single desktop Lighthouse score is not evidence that mobile visitors experience a fast portfolio. Collect a baseline for each template, record the device, viewport and test date, and distinguish synthetic test results from real-visitor measurements.

Core Web Vitals are one part of page experience, not a promise that performance work will automatically raise search rankings. Search relevance, useful project information and technical access still matter. A beautiful but empty page is not a successful portfolio merely because it loads quickly.

LCP, INP and CLS: which problem does each metric reveal?

MetricGood thresholdPossible portfolio issue
Largest Contentful Paint (LCP)2.5 seconds or lessMain render or video poster arrives too late
Interaction to Next Paint (INP)200 milliseconds or lessFilter, menu or lightbox responds sluggishly
Cumulative Layout Shift (CLS)0.1 or lessGallery, font or embed moves after it appears

These are the good-experience targets described by Google Search Central. In field reporting they are evaluated at the 75th percentile of actual page visits. A laboratory test is useful for finding a resource delay or long task; it is not a replacement for field performance. Small studios may have too little traffic to receive granular URL-level field data.

Check Search Console's Core Web Vitals report when it has sufficient data and use PageSpeed Insights for a combination of available field signals and lab diagnostics. Chrome DevTools can help identify which element becomes the LCP candidate and which JavaScript work delays a click. Note which page and conditions produced each result rather than treating an unlabeled score as a fact about every visitor.

A useful distinction

“The homepage passed a synthetic test” does not mean “mobile visitors have good Core Web Vitals”. Record the measurement source before making the claim.

Prioritise the first meaningful visual instead of the whole gallery.

On architecture websites the LCP element might be a large image, the main heading or a video poster. Identify it first. A hero inserted after a long JavaScript animation can leave an empty first screen even when the image file itself is relatively small. Keep the first meaningful image discoverable in HTML when practical, and provide suitable srcset and sizes for the viewport.

Do not mark an in-viewport hero image as loading="lazy". For the one genuinely critical image, fetchpriority="high" may help; giving every image high priority only creates competition. Above-the-fold assets may need a tested preload when hidden behind CSS or script-driven discovery. Follow web.dev's responsive image preload guidance and inspect the waterfall for duplicate mobile and desktop downloads.

Below-the-fold project thumbnails are different. They often benefit from lazy loading and responsive image derivatives, provided space is reserved before the download completes. Do not ship the full print master to a small phone thumbnail. For export size, format, crop and asset handover decisions, use the architecture portfolio image optimisation guide.

Let a hero film enhance the page, not hold it hostage.

Architectural films can communicate a space in a way that still images cannot. Yet asking a mobile visitor to download a large loop before the project name, introduction or navigation becomes useful makes the animation a barrier to the work. Give a hero film a meaningful poster image and keep essential project information readable independently of playback.

Where autoplay is justified, use muted playback, provide a way to pause and respect reduced-motion preferences. If a full embedded player is only needed after a click, defer its expensive scripts until the visitor chooses to play. A poster frame is an actual piece of content: select it carefully rather than relying on an accidental black frame or a low-quality thumbnail.

When a poster becomes the LCP element, prioritising the poster request can matter more than further compressing the video. The web.dev video performance guide discusses poster and player loading. For captions, controls and fallback content, follow the architectural film accessibility checklist. Video quality, visual accessibility and loading performance should be reviewed together.

Prevent layout shifts without sacrificing editorial typography.

When a gallery card has no known dimensions, the page can jump once its photograph arrives. Reserve image space using real width and height attributes or an intentional aspect ratio for the approved crop. When portrait and landscape layouts use different crops, verify the reserved dimensions on both breakpoints. Do not solve this with a single arbitrary height that badly clips an important piece of architecture.

Large studio typography can also cause shifts. A fallback font may wrap a heading differently from the final webfont, pushing the gallery and contact button down. Subset fonts where appropriate, choose a considered loading strategy, and test real line breaks before and after font swap. A font-display setting is not a substitute for checking the layout.

Watch for cookie banners, language controls, 360° embeds and captions that unexpectedly insert content above the reader's current position. Reserve room for components that belong to the layout, or use an intentional overlay without hiding important actions. Test a cold load, a return visit and a language switch. A static screenshot rarely reveals these defects.

The CLS target is not a request to freeze the entire site. Intentional changes triggered by a visitor can be legitimate. The problem is unanticipated movement that makes content difficult to read or causes someone to tap the wrong control.

A portfolio filter is only fast if tapping it feels fast.

Interaction to Next Paint measures responsiveness between an interaction and the resulting visual update. A project index may feel slow because selecting a category rebuilds a huge gallery, decodes many full-resolution images or triggers a script-heavy transition. A lightbox or 360° viewer can also delay the response to the next arrow or close control.

Test a representative gallery on a mid-range phone. Tap a category, open a project, change the image and close the viewer. Watch for delayed feedback, frozen scrolling or unexpected resets. Use Chrome DevTools to find long JavaScript tasks and whether time is spent before an event, in the event handler or waiting for the next paint.

Optimise the actual interaction: avoid reloading images unnecessarily, defer nonessential code, split expensive tasks and initialise interactive viewers only when needed. It is better to show a responsive first state than to block the browser while preparing every possible future state. The web.dev INP guide covers input delay and long tasks.

Keep keyboard access, visible focus, meaningful filter states and predictable lightbox dismissal intact. A site that reacts instantly to a mouse but cannot be navigated from a keyboard is not a successful experience.

Use a repeatable three-page release test, not a vanity score.

Pick the homepage, one image-heavy project detail and a project listing with a working filter or lightbox. Compare mobile first, then a second viewport. Keep the original creative brief in view: a clear architectural hero and legible project information are non-negotiable, but a surplus of unneeded downloads and third-party scripts is not.

Illustrative test record · not real Atmosferi metrics
PAGE: courtyard-house project (fictional) DEVICE / NETWORK: [record tested configuration] LCP ELEMENT: [identify in the browser trace] IMAGE CROP: [approved mobile and desktop variants] LAYOUT SHIFT: [font / image / embed / none] KEY INTERACTION: [filter / lightbox / menu / 360°] FIELD DATA: [available? source and date] ISSUE: [observed behaviour, not a guess] CHANGE / OWNER: [proposed fix, reviewer] RETEST: [actual result, page, date] RELEASE STATUS: [approved / not yet approved]

The labels are placeholders. They do not describe an audited project, measured performance or claimed client result.

Log the actual performance issue and how it changed after the fix. A CMS editor can undo an improvement by replacing a carefully optimised hero with a very large unprocessed export. Make performance part of the normal project-publishing process, not merely a developer's checklist at the initial launch.

Check the version that is really deployed on the public domain. A successful repository build alone does not prove that the intended release is visible to visitors. If the domain serves an older version, compare the production deployment and asset paths before judging a performance improvement.

Architecture portfolio Core Web Vitals launch checklist.

  • Compare homepage, project detail and project index on mobile and desktop.
  • Separate real-user field data from individual laboratory scores.
  • Identify the measured LCP element instead of assuming it is always the main photograph.
  • Keep the first meaningful image discoverable and avoid lazy loading it.
  • Serve responsive derivatives rather than print masters to every viewport.
  • Use priority hints selectively and verify they do not create duplicate downloads.
  • Provide a meaningful poster, pause option and sensible fallback for films.
  • Reserve stable space for gallery cards, images and late-loading embeds.
  • Check font swapping, heading wrapping and language-switch layout changes.
  • Test filters, gallery navigation, mobile menus and 360° controls for long tasks.
  • Keep keyboard behaviour and reduced-motion preferences working.
  • Retest after CMS uploads, design revisions and actual production deployments.
  • Record dates, devices and metric sources before making performance claims.

The target is not an architecture portfolio stripped of personality. It is a site where the architectural work appears promptly, its story stays legible and the viewer can explore without fighting the interface. Performance is a design constraint worth solving, not an excuse to remove the design.
