Architecture portfolio filters: design a project taxonomy that stays useful

An architecture portfolio needs a way to find relevant work, but filters can create misleading categories, duplicate URLs and empty pages. This guide sets out a practical project classification model for studios planning or maintaining a website.

Start with visitor questions, not a long list of tags

An architecture studio's portfolio often grows organically. One project is tagged “Residential”, another “Housing”, a third “Private house”. The CMS accepts all three, but the public website begins to look like three separate disciplines. A filter is useful only when it helps a visitor find comparable work. Start by writing down the questions the portfolio must answer: What kinds of projects does the practice undertake? Which work is completed, proposed or competition-stage? Can a potential collaborator find projects at a relevant scale? These questions are different from the internal folder names the team uses to store drawings.

Before adding a filter, test whether a visitor needs it. If the portfolio has twelve projects, a well-ordered index with clear captions may be more useful than six controls. Filtering is not a compulsory feature of a professional architecture website. The goal is to reduce the effort required to understand the work, not to demonstrate how many taxonomies a CMS can store.

Separate stable facts from editorial labels

Give every project a canonical record: a stable project ID, public title, slug, type, status, year definition, location at an appropriate level of precision, publication approval and a curated sequence of images. A project may have several functions, but its primary type should be chosen deliberately. Use a controlled list for categories, not free-form tags that editors invent during every upload.

Project status needs its own field. “Built”, “Under construction”, “Design proposal” and “Competition entry” are not building types. Mixing them into the same filter makes it impossible to compare like with like. Likewise, “2024” is ambiguous unless the site explains whether it means design, competition, completion or publication year. If that distinction cannot be maintained reliably, omit the year filter rather than implying precision.

Write a small category dictionary before building the UI

For each public category, record its display name, plain-language definition, inclusion rule and an example of what does not belong. A useful starting vocabulary might include Housing, Workplace, Civic and Cultural, Hospitality, and Interiors, but it should reflect the studio's actual work. Do not publish categories merely because other practices use them. If one project spans Housing and Interiors, decide whether it can appear in both and which category is primary.

Keep synonyms as search aliases rather than separate visible filters. For example, “residential” and “housing” can resolve to the same category when that matches the studio's editorial decision. If the studio works in several languages, translate the category meaning, not only the label. A German category and an English category should map to the same underlying identifier only when they genuinely describe equivalent scopes.

Handle small portfolios and empty states honestly

A portfolio with only one project in a category does not automatically need a category landing page. A page labelled “Healthcare” with zero public projects is worse: it suggests a capability without supporting evidence. Decide a minimum threshold for showing a filter, based on whether it helps users compare real work. Keep unpublished, embargoed and draft projects out of public counts.

When filters return no projects, explain the result and provide a visible “Clear filters” control. Do not silently reset the visitor's choices. If a category becomes empty after a project is withdrawn, remove the public filter option or give the category page a deliberate editorial purpose. Avoid creating indexable combinations for every category, year and status. Most filter states are interface choices, not distinct search landing pages.

Choose canonical project URLs before filtered views

Each project should have one durable detail URL. A visitor arriving from “Housing”, a search result or a shared link should reach the same canonical project page. Filter state can be encoded in the interface for navigation, but do not manufacture multiple indexable copies of the same project detail under every category path. If the website exposes filtered URLs, decide which views deserve a standalone page with unique editorial value and which should remain non-indexable UI states. Avoid conflicting canonical signals.

A project renamed after a competition or a practice rebrand should not simply disappear. Maintain a redirect from the previous URL and update internal links. The separate portfolio URL migration guide covers redirects and launch checks; taxonomy design determines what the destinations should be.

Fictional example: a mixed-use project in two categories

Fictional illustration, not an Atmosferi commission or a real client portfolio. Imagine a studio with fourteen public projects. One hypothetical scheme, “Canal Yard”, contains apartments above ground-floor shops and includes a separately designed lobby interior. Its primary type is Housing; a secondary editorial tag is Mixed-use. Its status is Design proposal. The project appears once in the main index, can be found through both relevant filters, and retains one detail URL. It does not appear in “Completed projects”, because a rendering is not evidence of construction.

If the studio has no other mixed-use project, it may choose not to display a Mixed-use filter at all. The project description can still explain the programme. The taxonomy serves the work rather than forcing the work into a large empty menu.

Make filtering work without a mouse

A project filter must be operable by keyboard and touch. Use actual buttons, checkboxes or select controls with visible labels, and indicate the active state in text rather than colour alone. Announce result-count changes accessibly where appropriate, preserve focus after selection and give users a straightforward reset. On narrow screens, do not hide the only route to a project behind a hover-only image grid.

Test the unfiltered view first: every project must remain discoverable without JavaScript-driven filtering where practical. If the interface needs JavaScript, provide a useful fallback or a clear accessible path. Ensure project cards have meaningful link text, descriptive image alternatives and stable layout dimensions. The portfolio image delivery guide addresses the performance side of a large project grid.

Test taxonomy changes as an editorial workflow

Give the studio a staging exercise before launch: add a project with two valid categories, change a proposal to completed only after approval, unpublish an embargoed project, rename a category, and remove the last project from a category. Check the public index, filter counts, project detail page, sitemap and internal links after each change. The CMS must not allow an editor to create a new public category accidentally by typing a slightly different spelling.

Document who approves category changes and how often the vocabulary is reviewed. A yearly check may be enough for a small practice; an active multidisciplinary studio may need more frequent review. The architecture portfolio CMS guide explains how to select an editing system around real tasks. This guide is about the editorial model the system must enforce.

A launch checklist for the project index

Before release, confirm that every visible category has relevant published projects; each project has one canonical URL; project types and statuses are not conflated; the unfiltered index works; the empty state offers a reset; keyboard and mobile navigation remain usable; no private work appears in filter counts; and the XML sitemap includes intended canonical pages rather than every filter combination. Ask one person unfamiliar with the studio to locate a housing proposal and a completed interior. Their difficulty is a more useful signal than the number of filter options.
