How to keep apartment availability accurate on a development website

A beautiful apartment selector becomes a liability when sales data goes stale. This practical workflow connects the sales team's decisions to trustworthy public unit statuses, with explicit fallbacks when updates fail.

Why an apartment can look available when it is not

A buyer opens a project website, filters for a two-bedroom apartment and finds a unit marked available. Meanwhile the sales team has placed it on hold. The page may have been correct yesterday, but a screenshot, an old brochure and a cached floor selector can continue telling three different stories. This is not primarily a 3D interface problem. It is a publishing and ownership problem.

The purpose of an availability workflow is not to promise that every unit can be reserved instantly. It is to make the website's displayed status traceable, timely and consistent with the sales team's actual process. A property website should not turn a provisional sales conversation into a contractual claim.

Define statuses before choosing software

Write down what each public label means and which internal events change it. “Available” should mean the team currently accepts enquiries, not that a reservation is guaranteed. “On hold” should have an owner, reason and expiry or review date. “Reserved” should reflect a defined internal milestone; “Sold” should be used only when the organisation's agreed completion condition has occurred. A “Not released” state is different from “Sold out”.

Separate internal workflow states from public wording. For example, an internal negotiation state may display as “Contact sales” rather than exposing private details. Decide whether prices are public, indicative or supplied on enquiry. Ask the project's legal and sales advisers to approve consumer-facing claims for the relevant market; this article does not establish legal definitions.

Pick one source of truth and name its owner

A spreadsheet can be a legitimate source for a small development if one person owns it and updates are controlled. A CRM or sales inventory system may be better when multiple agents, buildings and campaigns are involved. What fails is maintaining an independent website list, agent spreadsheet and brochure PDF without a reconciliation process.

Each unit needs a stable identifier that survives renaming in marketing materials. Record its building, floor, type, display name, public status, internal status, effective timestamp and last approved update. Keep floor area, orientation, plan revision and price in separately governed fields. Never infer availability from whether a unit appears in a visualisation.

Choose a publishing method that fits the sales operation

For a handful of units, a reviewed manual update with a daily check may be safer than a fragile integration. For a larger inventory, an authenticated feed can update the site automatically. Either way, define the update path from sales decision to public page, expected delay, error alert and responsible person.

Do not let an integration silently convert missing data into “Available”. Treat an unknown or failed feed as unknown. Log the last successful import, rejected rows and conflicting unit IDs. A publish job should validate allowed statuses, uniqueness of unit IDs and unexpected changes before replacing the visible dataset. Test the rollback path as carefully as the happy path.

What visitors should see when data is stale

A timestamp by itself is not enough if no one has decided when information expires. Set a freshness threshold based on how frequently units actually change. If the last verified update exceeds that threshold, replace definitive availability with a neutral “Confirm current status with sales” message, or temporarily hide the filter that promises live availability. Keep unit plans accessible where appropriate.

Do not use “live” or “real-time” merely because the website fetches a JSON file. A cache can be fresh while its upstream source is old. Check the age of the source record, not just the last browser request. If a site uses a CDN, specify cache lifetime and invalidation after a status change.

Fictional example: two channels disagree

Fictional example, not a real Atmosferi client or case study. Unit B-204 is marked “Available” on the website at 09:00. An agent records a temporary hold in the CRM at 09:12, but the website's scheduled import runs only every four hours. The page continues to accept enquiries that imply the apartment is free. The corrective workflow is to trigger an update on the hold event, show the last verified status and route new enquiries to the agent without promising availability.

Keep the floor selector, list and unit page consistent

The same unit should show the same public status in the building elevation, comparison table, search filters, individual unit page and enquiry form. Avoid hard-coding colours into an image that becomes outdated when a status changes. Use a shared unit record to drive every presentation. An interactive building diagram should not be the only way to find a home: provide a keyboard-accessible list and readable status text as well.

For deciding whether an interactive selector is justified at all, read the interactive floor-plan decision guide. That guide addresses presentation format; this workflow addresses the reliability of changing sales data.

Preserve context in the enquiry handoff

When someone enquires, send the stable unit ID, the status shown at submission, the page URL and the submission time to the authorised sales workflow. Show a confirmation that an enquiry was received, not that the unit was reserved. If a status changes while the form is open, warn the visitor and offer to confirm with sales before submission.

Collect only the contact information needed to respond and apply appropriate privacy notices and retention controls. Avoid exposing agent notes, buyer identities, hold reasons or internal pricing rules in public API responses. An internal inventory feed should never be treated as safe to publish without field-level filtering.

A release test for sales, design and development

Before launch, ask the sales owner to select a test unit and change it through every permitted state. Verify the unit list, floor selector, unit detail, enquiry form and mobile view after each transition. Simulate a failed import, duplicate unit ID, removed unit, stale timestamp and delayed cache invalidation. Check that search engines and shared social previews do not present an old status as a guarantee.

Document who can correct a wrong status outside office hours, who approves public labels and how an erroneous update is rolled back. Record the tested source version and date. A short operational checklist is more useful than an elaborate interface nobody knows how to maintain.

What to include in the handover

Hand over the unit data dictionary, status definitions, update ownership, sync schedule or trigger, error notifications, fallback copy, audit trail and a short procedure for a sales-team member to correct a record. Include access rules, backup and rollback instructions. Rehearse one complete update without the website developer present.
