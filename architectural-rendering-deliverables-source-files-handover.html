Architectural rendering deliverables: source files and handover checklist

A finished image, an editable Photoshop document and a native 3D scene are three different products. Define the handover before the project reaches final approval.

Define what is actually being handed over

A final rendering is not the same deliverable as an editable 3D scene. Before production begins, distinguish presentation images, print masters, layered retouch files, camera settings, asset lists and native scene files. The brief should say which are included, which are optional and which are excluded. A JPEG can be perfectly suitable for a planning presentation but cannot replace a model when another team needs to change geometry. Neither side benefits from discovering that distinction after final approval.

Make a deliverables matrix before the first preview

For each output, record purpose, file type, dimensions, colour space, expected editability, naming convention, revision number and recipient. Separate a web-ready image from a print master even if both depict the same camera. For an animation, identify the video master, compressed review copy, frame rate, resolution and whether individual frames are required. For a virtual tour, specify whether the handover is a hosted experience, panorama files or a transferable project package. This prevents the phrase 'all files' from silently expanding into incompatible expectations.

Specify raster image masters and review copies

A review JPEG is convenient for fast comments, while an approved high-resolution master may need a lossless format. Agree on pixel dimensions rather than vague terms such as 'high quality'. If the image will be cropped into multiple layouts, discuss safe margins before rendering. Confirm colour profile and whether transparency is needed. A TIFF or PNG is not automatically better for every downstream workflow; the destination software and intended use determine the useful format. Preserve an untouched approved master separately from social-media crops and annotated review exports.

Clarify what a layered file can and cannot edit

A layered Photoshop document may contain sky, people, planting, grading and masks, but it does not necessarily contain editable building geometry, physically correct reflections or an independent light setup. Ask which adjustments the client expects to make: replacing a background is different from moving a wall. If layered delivery is agreed, define which layers must remain separate and whether linked assets and fonts are supplied. Some third-party assets cannot be redistributed. A flattened final image should remain the visual reference against which the layered file is checked.

Treat native 3D scenes as a separate technical package

A 3D scene may depend on a specific renderer, software version, plugins, proxies, texture paths, purchased libraries and external references. Merely sending a scene file does not guarantee that another workstation can open it or reproduce the image. Agree whether the handover must be editable, renderable or only inspectable, then test on a clean machine or documented equivalent environment when practical. Record missing dependencies honestly. If the originating model came from the architect, distinguish that input from the visualisation artist's working scene.

Separate possession of files from permission to reuse them

Receiving a file does not, by itself, settle copyright ownership, publication permission, modification rights or rights to redistribute embedded third-party assets. Confirm the contract and any licences before assuming a native scene, stock photograph, person cut-out or commercial 3D model can be transferred to another supplier. Different jurisdictions and contracts may produce different outcomes; this is a production checklist, not legal advice. Record permitted uses such as marketing, planning submissions and portfolio display separately, and ask a qualified adviser when rights are unclear.

Tie final delivery to a named approved version

Use one approval reference for each camera, with a timestamp or revision ID and an unambiguous filename. The approved image should match the final exported master, not an earlier preview with slightly different vegetation or glazing. Keep an issue log for unresolved changes and mark them as accepted, deferred or outside scope. If the architect changes a design after approval, treat the updated view as a new revision rather than silently overwriting the old master. The rendering feedback checklist covers the review process in more detail.

Use names that survive email and shared drives

A practical naming pattern includes project code, view ID, stage, revision and output purpose, for example PROJECT_A_EXT03_R04_PRINT.tif. Avoid relying only on 'final', 'final2' or a personal folder structure. Keep a small manifest listing every delivered file, size and intended use. A checksum can help verify large archives after transfer, but it does not replace opening the files. Make the manifest readable without specialised software so the project team can locate assets months later.

Plan transfer, storage and access expiry

Large archives are often shared through temporary download links. Agree who downloads them, where the approved masters will be archived and how long the transfer link remains active. Restrict access to project participants when material is confidential or unreleased. Do not place sensitive floor plans or unapproved marketing imagery on a publicly indexed folder merely for convenience. Confirm that the client has successfully received and opened the package before allowing the link to expire. Retention periods should be contractual rather than guessed.

Design for the next supplier without promising full portability

A future visualisation team may use different software. A neutral geometry export can preserve basic shapes but may lose modifiers, shaders, scattering, lighting and camera fidelity. Include a brief handover note with units, coordinate system, major dependencies and known limitations when model transfer is in scope. For continuing work, a reference render and annotated material schedule are often as valuable as the model itself. Do not promise that a native scene will render identically in another engine unless that exact pipeline has been tested.

Fictional illustrative example: three apartment marketing views

Imagine a fictional housing project requiring three approved exterior images for a brochure and website. The architect requests 6,000-pixel print masters, smaller sRGB JPEGs and one revision manifest. No editable 3D scene is included. Later, the developer asks another agency to animate the building. The delivered images are useful references, but they cannot supply a camera-ready animated scene. Had animation or transferable model files been part of the original scope, the team could have planned asset licences, scene dependencies and fees at the outset. This example is fictional and does not describe an Atmosferi commission.

Final handover checklist

Before closing the project, confirm: the signed-off camera list matches delivered files; image dimensions and colour profiles match their destinations; filenames identify the approved revision; all links open; layered and native files are included only where agreed; dependencies and limitations are documented; redistribution permissions have been checked; a recipient has verified the archive; and an agreed owner is responsible for long-term storage. A short written handover record is more reliable than an informal message saying that everything has been sent.
