Multilingual architecture portfolios: a launch QA checklist

Make multilingual project pages genuinely useful, technically consistent and maintainable without publishing empty translations.

By Michal Kašpárek, architect and founder of Atmosferi8 November 2026

Architecture portfolios are unusually hard to localize well. The same project can have a different public status, description, credits and audience in each language. This checklist is for studios and developers maintaining a real multilingual site. It is not a promise of search rankings or a substitute for editorial review.

Start with the visitor's task, not a country-page quota

An architecture studio may work in several languages, but that does not mean every project needs four near-identical pages. Decide which audiences genuinely need a translated project description, service explanation and contact route. A short English summary for an international jury is a different product from a complete German project page for prospective clients. Record those decisions before designing the language switcher.

A multilingual portfolio fails when visitors land on a project photograph with a translated menu but untranslated context. The test is whether a visitor can understand the project's status, location, contribution and next step in the selected language.

Create a language-by-project content matrix

List every public project with a stable internal project ID. Add columns for the language of each available page, title, short summary, location, year or status where approved, services performed, credits, image captions, publication permission, reviewer and URL. Mark missing translations as missing, not 'done' because a template has been localized.

Use separate status values: not planned, draft, technical review, approved and published. That makes it possible to publish an English-only competition entry without accidentally promising a nonexistent Czech equivalent. A content matrix also exposes inconsistent project names across languages.

Translate architectural meaning rather than interface strings

Project descriptions contain technical terms, local planning vocabulary and design claims. Have an appropriate reviewer check terminology, not just spelling. Preserve names of buildings and proper nouns unless an established translated name exists. Keep the actual scope of the studio's involvement explicit: concept design, competition entry, built work or visualization are not interchangeable.

Do not invent floor areas, awards or sustainability certifications to make a translation more complete. When the source description is uncertain, return the question to the project owner. A translation should not quietly become a stronger marketing claim than the original.

Choose predictable URL structures

Give each fully translated project a stable, crawlable URL. Language directories such as /en/projects/example/ and /de/projekte/beispiel/ can work, as can a documented alternative. What matters is consistent linking, a page that loads without client-side language detection and a URL that remains usable when shared.

Avoid forcing visitors onto a language version based only on IP address. Let them change language and return to the same project where a true counterpart exists. If no counterpart exists, the language switcher should explain the fallback or link to the language's project index, rather than pretending a different project is the translation.

Make every genuine translation self-canonical

A fully translated English project page should normally point its canonical to its own English URL, and the German equivalent to its own German URL. Do not canonicalize the German page to English merely because both describe the same building. That would undermine the purpose of maintaining separate language pages.

Check that the declared canonical is absolute, indexable and responds successfully on the intended public host. Remove accidental staging hosts, query-string language toggles and redirects from canonical targets. A canonical is a hint to search engines, not a guarantee of indexing.

Build hreflang clusters only from real equivalents

For each set of genuinely equivalent pages, declare their language codes and absolute URLs consistently. Every member should reference itself and its peers; the peers should return the same relationship. Use the language code that matches the actual copy, not the location of the architecture project. A German-language page about a Norwegian building is still German-language content.

Do not add hreflang between an English project page and a German services page. They answer different questions. Likewise, a two-paragraph teaser is not necessarily a complete equivalent of a detailed case study. If a language version is absent, omit that alternate until the content exists. An x-default choice is optional and should point to a useful fallback, not a fictional universal translation.

Fictional example: one project in two languages

Imagine a fictional architecture studio with a completed project page in English and German, while the Czech version remains a draft. The English page is at /en/projects/courtyard-house/ and the German page at /de/projekte/hofhaus/. Both have their own canonical URLs and reciprocal en/de hreflang. The Czech draft is excluded from the cluster and from public navigation.

The project title, drawings and photographs can be shared where the studio has publication rights; the written captions, contribution statement and enquiry route must still be checked in each language. This example is illustrative, not an Atmosferi client project or a claim about an existing deployment.

Keep photographs, plans and credits accurate in every locale

A single image may be reused across translated pages when its license allows it, but the surrounding editorial context must remain accurate. Translate descriptive captions and meaningful alternative text when appropriate. Keep photographer, collaborator and copyright credits faithful to the source agreement; do not translate personal names or silently remove attributions.

If an image shows an unbuilt proposal, label it as a visualization in every language. If the image is a concept, distinguish it from a built commission. A translated caption must not convert 'proposed' into 'completed'. For media performance, use the separate portfolio image optimization guide.

Test language switching at project depth

Open a project detail page, switch languages and verify the destination. Repeat from project listings, the contact page and the footer. Confirm that the language menu has clear accessible labels, visible focus states and a usable mobile layout. The current language should be identified without relying only on color.

When a corresponding project page does not exist, prefer an honest fallback to a broken deep link. A user should never be trapped in a loop of automatic redirects. Check the switcher with a keyboard and at narrow screen widths, not only on a desktop hover menu.

Run a small automated URL audit

Export the public URL inventory and validate each entry: expected language, one H1, title and description, robots directive, canonical, HTTP response, outgoing internal links and declared alternates. Compare the alternates as a graph to catch missing reciprocal links. Then regenerate the XML sitemap from the indexable public pages, rather than maintaining a second handwritten list.

Automated checks catch missing tags but cannot judge whether two pages are truly equivalent or whether architectural terminology is correct. Keep a human editorial review in the release checklist. Test the production host separately from preview: a successful preview build does not prove that the public URL is reachable.

Release in controlled batches

Publish only reviewed translations. After deployment, sample at least one page from each language, one project with two translations and one project intentionally available in only one language. Confirm their public HTTP responses, visible copy, canonical and alternates. Inspect mobile navigation and verify that images and captions match the selected language.

A sitemap submission or a successful deployment status is not evidence that search engines have indexed a page. Record the release date, the exact URLs tested and the person who approved each locale. If a page later changes status, update the content matrix before changing the alternate cluster.

Give the studio an editorial maintenance rule

Document who can add a project, who approves translations and who checks the technical fields. A lightweight CMS should prevent editors from selecting a nonexistent translated counterpart. Give each project a stable internal identifier so URL changes and localized titles do not sever the relationship between versions.

A quarterly review can identify stale project statuses, dead contact links and translations that lag behind the source. The portfolio URL migration checklist covers redirects and relaunch mapping; this guide focuses on multilingual equivalence and ongoing editorial quality.

Pre-launch acceptance checklist

Before sign-off, confirm: every published locale has reviewed architectural copy; project status and credits agree across languages; each public page has a unique self-canonical; hreflang clusters contain only full equivalents and are reciprocal; the language switcher has an honest fallback; mobile and keyboard navigation work; sitemap entries match public indexable URLs; and representative production URLs return the expected response.

Keep the results as a short release record with URLs and dates. If any condition fails, leave the affected translation unpublished rather than shipping a misleading language variant.
