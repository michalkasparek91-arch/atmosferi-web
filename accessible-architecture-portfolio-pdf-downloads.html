Accessible architecture portfolio PDFs: how to publish project sheets people can actually use

A practical editorial and technical review for architecture studios exporting project sheets, plans and brochures as downloadable PDFs.

By Michal Kašpárek, architect and founder of Atmosferi9 November 2026
In this guidePurposeSource contentReading orderPlans and sectionsImage alternativesLinks and metadataMobile reviewFictional exampleAcceptance test

Architecture project PDFs are often designed for a printed spread, then placed online without another thought. That leaves an avoidable gap between an attractive document and a usable one. This checklist focuses on document structure, drawing explanations, export settings and practical testing.

Define what the download is for

A downloadable project sheet is not automatically a better version of an architecture website. Some visitors need a printable summary for a tender meeting; others need to zoom into a plan or share a project internally. Decide which task the PDF solves before laying it out. A beautiful 40-page image-only portfolio may be impossible to search, read aloud or navigate with a keyboard.

This guide addresses the downloadable document, not the project page itself. For selecting photography and writing project descriptions, start with the project-content preparation guide. Keep essential project facts in HTML too; do not make a PDF the only route to understanding the work.

Build from structured source content

Prepare a short project record: title, location at an appropriate level of precision, project status, studio role, year or phase, short description, image credits and drawing captions. Use real headings and paragraphs in the authoring file rather than manually positioning every line as a decorative text box. Exporting from a visually arranged page does not guarantee a usable reading sequence.

Keep a source file and an export checklist together. If the plan changes, the project status changes or a photographer requests a credit correction, the PDF should be rebuilt from that controlled source instead of patched as an untracked duplicate.

Check reading order independently of appearance

Reading order is the sequence assistive technology encounters. A two-column spread may look obvious to a sighted reader but be exported as left heading, right heading, left paragraph, right paragraph. Inspect the tagged PDF structure and read it in sequence with a screen reader or a document accessibility checker. A heading should lead to its own text; a caption should remain associated with its image.

Do not rely on the visual page number alone for navigation. Give a multi-project PDF meaningful bookmarks and a sensible document title. Check that keyboard focus reaches links in a logical order. A print spread can still be elegant without forcing everyone to decipher its layout.

Make architectural drawings understandable

Plans, sections and diagrams often carry the most important information and the least accessible text. A rasterised plan cannot be understood by text extraction alone. Provide a concise text description of what the drawing communicates: for example, the relationship between a public entrance, a central courtyard and the main circulation route. Do not attempt to narrate every line weight or hatch.

Retain readable room labels where possible, use adequate contrast and provide a separate enlarged drawing or accessible HTML explanation when the plan is too dense at page scale. Mark purely decorative graphic elements as artifacts in the tagged structure so they do not interrupt the reading sequence.

Write alt text that explains the architectural point

An exterior hero image may need a description of massing, materials and site relationship, not the phrase “beautiful building”. A close-up of a facade junction may need to explain the junction. Avoid duplicating the nearby caption word for word; the alternative should add the information someone misses by not seeing the image. If the photograph is decorative and its information is already stated in text, it may not need separate spoken content.

Credit and permission are different questions from accessibility. Keep the authorised photographer or visualisation credit visible and verify reuse rights using the portfolio attribution workflow. Alt text is not a substitute for an image licence.

Preserve useful links and document metadata

Use descriptive link text such as “View the full courtyard project” rather than “click here”. Confirm exported links are active and have an identifiable target. Include a document language, descriptive title and appropriate heading hierarchy. Check that text remains selectable and searchable; a PDF made of full-page screenshots usually fails that basic test.

For a public download, show its format and approximate size beside the link on the website. People on mobile connections should know what they are opening. Offer the HTML project page as an alternative, not a forced download or an unexplained new tab.

Test the file on a phone, not only a desktop

A fixed-page PDF is inherently less adaptable than responsive HTML. Test at ordinary phone width: can someone zoom into a section without losing their place, follow a link, read a caption and return to the website? Long landscape spreads and tiny plan legends are frequent failure points. If the file only works at A3 on a large monitor, provide a simpler mobile-friendly summary.

Optimise images for the intended document use without stripping the linework needed to understand drawings. A compressed brochure can be smaller but still unusable. The image optimisation guide explains the related distinction between master files and delivery derivatives.

Fictional example: a housing project sheet

Fictional illustrative example, not an Atmosferi client project: a studio publishes a six-page housing project PDF with a cover rendering, site plan, two floor plans, a section and credits. The first export is a set of flattened pages. It looks consistent, but none of the headings are tagged, the plan labels are unsearchable and the website says only “Download”.

The revised version keeps selectable text, tags the heading sequence, adds a short explanation of the plan's circulation logic, provides a link to the HTML project page and labels the download “Housing project summary (PDF, approximate file size)”. The studio checks the exported reading order rather than assuming the source layout has preserved it.

Use an acceptance test before publishing

Ask a reviewer who did not design the document to complete these tasks: identify the project's status and the practice's role; navigate by headings or bookmarks; find the entrance in the plan description; open the project link using a keyboard; locate the image credits; and read the document on a narrow phone screen. Record failures and retest the actual final PDF after export.

A PDF accessibility checker can flag missing tags or metadata, but an automated pass does not prove the drawing descriptions are useful or that the reading order makes sense. Keep the checklist with the final export date and file version. If an accessible document cannot be produced within the project constraints, publish the substantive content in accessible HTML and explain the limitations of the download.
