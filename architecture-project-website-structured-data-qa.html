Structured data for architecture project pages: a practical QA workflow

A practical way to make project-page metadata accurate, consistent and maintainable, without inventing building facts or expecting automatic search enhancements.

By Michal Kašpárek · Atmosferi°21 November 2026

Start with the page, not a schema generator

Architecture portfolios often combine completed buildings, proposals, competition entries and images produced by several teams. Structured data is a machine-readable description of the page, not a second opportunity to embellish the project. Start by identifying what the URL actually represents: a project story, a studio service, an image gallery or a sales listing.

For an editorial project page, a modest WebPage description is often more defensible than an elaborate claim that the page describes a particular type of building. Use Article only where the page genuinely presents an authored editorial article. Neither type guarantees a search enhancement. Keep the visible project title, status and credit information aligned with the markup.

Make a field-by-field evidence register

Before adding JSON-LD, record the page URL, visible title, language, publication date if genuinely known, author or publisher where appropriate, project status and the source that confirms each value. Mark unknowns as unknown. A content management system should not silently fill missing completion years, architects or addresses with defaults.

Separate the author of a website article from the architect who designed the building, the photographer who made the images and the visualisation artist who created renders. These are different roles. Do not assign all of them to the publishing studio simply because its logo appears in the header.

Choose a restrained schema graph

A useful starting point is one WebPage node with a stable @id, canonical url, name, description and inLanguage. An editorial project article can add an Article node linked through mainEntity and mainEntityOfPage. Only include datePublished when the actual publication date is known. A date when the building opened is not the publication date of the webpage.

Do not add LocalBusiness to every project because the studio has an office, or use Product merely because a developer sells units elsewhere. These types describe different entities and can introduce inaccurate claims. If the site has a separate business profile, keep that entity distinct from individual project pages.

Fictional example: a competition proposal

Fictional illustration, not a client case study: A studio publishes a page titled “Riverbank Library Concept”, explicitly marked “unbuilt competition proposal”. Its schema can describe the page itself without asserting that a completed public library exists at a precise street address. The example below uses placeholder URLs and must not be copied into production unchanged.

{
  "@context": "https://schema.org",
  "@type": "WebPage",
  "@id": "https://example.org/projects/riverbank-library#webpage",
  "url": "https://example.org/projects/riverbank-library",
  "name": "Riverbank Library Concept (unbuilt proposal)",
  "inLanguage": "en",
  "description": "Fictional unbuilt competition proposal."
}

Notice what is absent: an invented opening date, client testimonial, star rating, precise location and claim of completed construction. A structured-data graph can be deliberately small and still be accurate.

Run four distinct checks before release

  1. Syntax: Parse every JSON-LD script as JSON. Catch invalid quotation marks, trailing commas and escaped content copied from a CMS.
  2. Identity: Compare each declared URL with the final canonical URL after redirects. Check that IDs are stable and that language values match the rendered page.
  3. Truth: Read every property against the visible page and the approved project information. Remove unverifiable awards, dates, roles, addresses and status claims.
  4. Rendering: Inspect the published HTML, not just the editor preview. Confirm the script is present in the delivered document and that deployment or templating has not duplicated contradictory graphs.

Schema.org validation helps with vocabulary and structure. Google's Rich Results Test checks eligibility for supported search features, not whether every schema type receives a rich result. Neither tool independently verifies the truth of a project's claims.

Plan for changes in project status and credits

A concept may later be built, an embargo may lift, or a collaborator may request a credit correction. Update the visible page first, then the structured data, then review the canonical and any internal links. Keep a short change log identifying the editor and the approved source of the new fact.

When a project moves to a new URL, treat that as a migration problem rather than generating two contradictory schema identities. Preserve the canonical decision and redirect strategy. When an image is withdrawn, remove unsupported image metadata and references to that asset as well.

Release checklist for the editor

  • One public canonical URL matches the JSON-LD page URL.
  • Project status is clear: built, in progress or proposal.
  • Authorship and design credits describe the correct roles.
  • Unknown facts are omitted rather than guessed.
  • All JSON-LD blocks parse and linked IDs resolve consistently.
  • Dates refer to publication or modification of the page, not construction milestones.
  • Language matches the visible copy; alternates exist only for complete equivalents.
  • Mobile page content and schema describe the same project.
  • After deployment, inspect the actual public HTML and revisit after significant updates.

The goal is a trustworthy, maintainable project page. Structured data is useful documentation for machines, not a substitute for a readable portfolio or a shortcut to search rankings.
