Property development website enquiry handoff: keep the unit and buyer context intact

A buyer selects a home, but the sales team receives an anonymous “contact me” request. Here is a practical specification for moving the right information from a development website into a responsible sales workflow.

Why a working form can still lose the buyer

A buyer selects apartment B-204, asks for a viewing and submits a form. The website reports success, yet the sales team receives only a name and a generic message. The person must explain the apartment again, while the team cannot reliably tell which floor plan or availability status they saw. The problem is not visual design; it is the handoff contract between the public website, form processor and sales workflow. Treat that handoff as a product feature with a defined owner and acceptance tests.

Define the minimum useful enquiry record

Agree the fields before designing the form. A practical record includes a unique enquiry ID, creation timestamp with timezone, development identifier, unit identifier when applicable, enquiry type, contact details the buyer chose to provide, preferred contact channel and the text they submitted. Include the source page or campaign only when appropriate and lawfully collected. Preserve a human-readable unit label alongside a stable internal ID, because marketing names can change. Do not silently add sensitive profiling fields just because the CRM has empty columns.

Separate the unit ID from its display label

A plan selector might display “Two-bedroom, level 3” while the underlying inventory system calls it B-204. Pass the immutable inventory key, not just the visible label or a screenshot. At the receiving end, resolve that key against the authoritative inventory record and display its current status. The website should also record which information version the visitor saw, where technically feasible. Never assume that a unit was still available when a salesperson opens the enquiry later. The separate availability synchronisation guide explains the publication side of that problem.

Keep consent and enquiry processing distinct

A request for a viewing needs contact details to be handled, but it does not automatically grant permission for unrelated newsletters. Explain who receives the enquiry and why, link to the applicable privacy information and record any optional marketing preference separately. Use an unchecked optional choice when consent is the appropriate legal basis. A project team should obtain jurisdiction-specific legal advice on lawful bases, retention and processor arrangements rather than copying a generic checkbox. Never include unnecessary personal data in URLs, analytics events or browser console logs.

Give every enquiry an accountable destination

Define a routing table by development, enquiry type and responsible sales team. Specify the fallback when a salesperson leaves, an inbox is full or the CRM is unavailable. A shared mailbox alone is not a workflow: assign ownership, a status such as new / assigned / contacted / closed, and a way to detect unassigned records. Avoid promising a response time on the public website unless the team can actually support it. When an enquiry is reassigned, preserve the original unit and message context.

Design for retries without duplicate leads

Forms and integrations fail in ordinary ways: a visitor double-clicks submit, a network request times out after the server accepted it, or a CRM API rejects a field. Use an idempotency key or equivalent duplicate-control mechanism so retries do not create several sales tasks for one submission. Distinguish a confirmed receipt from an attempted send. If the website cannot verify acceptance, show an accurate failure or retry message rather than an unconditional “Thank you, we received it.” Protect the endpoint against spam and rate abuse without blocking legitimate buyers using assistive technology.

Fictional example: two enquiries for the same apartment

Fictional workflow, not a client project or measured result. A visitor opens a hypothetical unit C-12 and submits a viewing request. The site creates enquiry E-1048, associates it with inventory key C-12 and sends it to the development’s assigned team. The CRM temporarily times out; the integration retries with the same idempotency key. The receiving system creates one record, not two. By the time the agent opens it, C-12 has been reserved. The agent sees the current status and the originally requested unit, so they can respond accurately without treating the earlier availability display as a promise.

Test the full journey on a narrow phone screen

A mobile user may arrive from an apartment card, tap “Ask about this home” and be redirected to a form. Preserve the selected unit across that transition. Use visible labels, appropriate input types, clear error messages and a focus order that works with a keyboard and screen reader. Do not hide the only enquiry path inside a hover interaction on an interactive plan. The interactive floor-plan guide covers equivalent list navigation and unit selection.

Run an end-to-end release checklist

Test a valid unit enquiry, a general development enquiry, a unit whose status changed, a duplicate submission, a CRM outage, a routing fallback, a consent refusal and a form with invalid fields. Verify what the buyer sees and what the salesperson actually receives, including timezone and unit key. Check that internal logs exclude unnecessary personal information. Retest after inventory, CRM schema or form changes, not only at launch. The development website launch checklist covers the wider publication package. An attractive website is useful only when the next person in the process can act on the information it sends.
