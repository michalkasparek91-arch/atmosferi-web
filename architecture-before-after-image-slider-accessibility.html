Before-and-after architecture image sliders: how to make comparisons accurate and accessible

A publishing and quality-assurance workflow for architecture practices using interactive existing-versus-proposed image comparisons on their websites.

By Michal Kašpárek, architect and founder of Atmosferi9 November 2026

A swipeable image comparison can clarify a renovation in seconds. It can also conceal differences in viewpoint, exclude keyboard users and imply that an unbuilt proposal is complete. This guide focuses on the website comparison component, not the architectural modelling or approval of the two images.

Decide whether a slider is the right format

A before-and-after slider is useful when two images share a meaningful viewpoint and visitors need to inspect a local change. It is a poor choice when the original and proposed cameras differ, when the comparison needs annotations, or when a visitor must see both versions simultaneously to understand the decision. Start with a static side-by-side pair as the editorial baseline. Add an interactive slider only when it improves that comparison. A slider is a presentation control, not evidence that the proposal has been approved or built.

Audit the image pair before building the interface

For photographic renovation comparisons, record the source of each image, capture date, camera position, lens or field of view when known, crop and image status. Do not stretch one frame to match another. Differences in season, weather, exposure, planting or temporary objects can create a misleading impression of improvement. Where the images cannot be matched, label them as illustrative views rather than a direct before-and-after comparison. The camera-matching checklist explains the photographic alignment problem; this guide addresses the website interface after the images are prepared.

Make the two states unambiguous

Use visible labels such as “Existing condition, photographed March 2026” and “Proposed design, visualisation, revision B”. The labels must remain readable as the divider moves and should not depend on colour alone. Give each image its own meaningful alternative text describing the architectural differences, not simply “before” and “after”. Include a short plain-language summary beneath the comparison so the key change is available without operating the widget. Keep any unverified completion or consent claim out of the caption.

Treat the divider as an actual control

A draggable line that responds only to a mouse excludes keyboard and many assistive-technology users. If the widget behaves like a slider, expose an accessible name, a current value and minimum/maximum bounds, and support arrow-key adjustment with a visible focus indicator. Test that the control can be reached, adjusted and exited using only the keyboard. A custom div with a drag handler is not sufficient merely because it looks like a slider. Native controls or a carefully tested accessible implementation are safer than a visually clever interaction with no semantics.

Prevent the comparison from trapping mobile users

On a phone, the divider may occupy the same gesture area people use to scroll. Test a narrow viewport with one hand: can visitors scroll past the comparison without accidentally dragging it, move the handle deliberately, and identify both states without zooming into tiny labels? Give the handle a comfortable touch target and keep its position within the image. The image pair should scale to the available width without horizontal page overflow. Never hide the only explanation behind hover.

Provide a useful no-script and reduced-motion experience

The page should remain understandable when JavaScript fails, the widget cannot initialise or an assistive technology cannot operate it. Show the two labelled images in a normal document flow as the default, then progressively enhance to a slider. Do not load both images as inaccessible CSS backgrounds with no text alternatives. If the handle animates, respect reduced-motion preferences. Keep an explicit “View images separately” route or an adjacent static pair when the interaction cannot be made dependable.

Budget for two large architectural images

Comparison widgets can accidentally download two full-resolution render masters even when the display is only a few hundred pixels wide. Export appropriately sized responsive derivatives and preserve the same crop for both states. Reserve the image area's dimensions to avoid layout shifts when assets arrive. Use modern formats where supported, but retain a reliable fallback. Test a throttled mobile connection: the page should not display a misleading single state while the other image is still loading. Do not confuse visual sharpness with unlimited file size.

Separate visual storytelling from project evidence

A slider makes a change feel immediate, which is exactly why its claims need care. For planning or public consultation, retain the source drawing revision, survey limitations, image date and any material assumptions outside the interaction. If a retained wall, tree or neighbouring building is omitted in the proposed frame, verify that omission against the design rather than treating it as a retouching choice. The existing-versus-proposed fabric review covers the architectural accuracy of the underlying images; a slider cannot repair an inaccurate source pair.

Fictional example: a courtyard refurbishment

Fictional illustrative example, not an Atmosferi client project. A practice publishes a courtyard refurbishment with a photographed existing condition and a proposed render. The first widget opens with the divider at the far right, has no keyboard control and labels the proposal “After”, although construction has not started. A revised page uses the label “Proposed design”, starts at a neutral divider position, provides keyboard and touch operation, and shows the two labelled images separately if the script fails. The team also adds a one-sentence explanation: the proposal replaces an impermeable paved area with planting and a pedestrian route. The example demonstrates presentation decisions, not verified environmental outcomes.

Run a task-based publication test

Ask a reviewer unfamiliar with the project to identify which state is existing and which is proposed, explain the architectural change without dragging the handle, operate the divider by keyboard, scroll past it on a phone, and read the content with images disabled. Then disable JavaScript and repeat the core comprehension task. Verify that the final image pair matches the approved project revision and that image credits and reuse permissions are recorded. A successful animation is not the acceptance criterion; accurate understanding is.
