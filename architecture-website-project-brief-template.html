How to brief a website designer for an architecture practice

A useful website brief identifies the audience, project archive, publishing workflow and actual handover requirements before anyone prices a new homepage.

Start with a decision, not a visual reference

A brief for an architecture practice website should explain what the new site must help people do. A beautiful reference site is useful for discussing tone and hierarchy, but “minimal, modern and premium” does not tell a designer which clients the studio wants to attract, what those clients need to read or what a successful enquiry looks like.

Write one primary purpose and no more than two supporting goals. A practice might prioritise clearly presenting completed residential work and making it easier for potential private clients to enquire. A different office might need a credible archive for public procurement. These goals create different navigation and content requirements, even when both websites share an understated visual style.

Describe who should use the website

Name the audience in ordinary language: private homeowners, residential developers, institutional clients, collaborators, potential employees or journalists. Record the problems they are likely to arrive with and the information they need before contacting the practice. Keep the list short enough to guide trade-offs.

If the studio offers work in several regions, specify the territories it actually serves and where local professional rules affect delivery. A website can showcase international work without promising statutory services in every jurisdiction. Link each major audience to the most relevant projects, genuine service descriptions and contact route.

Inventory the existing site and its problems

Include the old domain or URL if there is one, the content worth keeping and the frustrations that triggered the redesign. Typical questions include whether visitors can find projects by type, whether mobile images are readable, whether enquiries arrive reliably and whether the team can publish new work without a developer. Record actual evidence where available, rather than guessing which design detail harms conversion.

Ask the provider to map retained pages and incoming links before launch. A redesigned homepage is not a reason to abandon useful project addresses. Use the architecture portfolio migration checklist for redirects, canonical URLs and content preservation.

Count the projects and reusable page types

List the number of projects you intend to publish now, the expected pace of new projects and the differences between them. A portfolio with fifteen projects built from one reusable template is not the same scope as fifteen individually designed case studies. Identify the necessary page types: home, work index, project detail, studio, services, journal, contact or a separate development microsite.

Give the designer two representative projects with differing needs, such as a built house with photographs and an unbuilt competition scheme with renders and drawings. If those can be handled well, the content model will be easier to plan. The project case study guide explains how to structure individual project pages without turning every project into the same image stack.

Say which photographs, drawings and texts are really ready

For each shortlisted project, mark available photos, renderings, plans, captions, credits and permissions. Separate existing source material from assets already cleared for web publication. Owning a file does not necessarily mean holding the licence to publish it; a supplied BIM model does not automatically provide polished website visuals.

Separate essential functions from optional ideas

Put requests in three groups: needed at launch, useful later and not required. A straightforward practice portfolio may need a searchable project archive, simple contact method and lightweight project editor. An apartment sales site may need unit data, enquiry routing and inventory synchronisation. Treat film, 360-degree tours and interactive plans as distinct deliverables with their own inputs and acceptance conditions.

Do not mix visual ambition with technical requirements. “Full-screen film on the homepage” describes a presentation idea; the brief should also state how the page works for reduced motion, slow connections and visitors who cannot play video. Avoid including features solely because they appeared in a reference website.

Describe what the team must edit after launch

Write down the actual publishing tasks: add a project, change its category, replace a photo, update a service, publish a journal article or adjust team profiles. Identify who will edit content, who approves publication and whether multiple languages must be updated. Ask for a demonstration of these tasks before the CMS is considered finished.

Do not request a platform by name without also documenting the editing workflow you require. The architecture CMS comparison guide covers static, conventional and headless approaches, including content ownership and export.

Treat languages as content responsibilities

State the source language and every language that needs a complete public version. Decide who supplies translations, who reviews professional terminology and whether a new project must launch in all languages simultaneously. A flag or language switch is not a translation plan.

If only some projects are translated, tell the designer how to handle missing versions without sending visitors to unrelated content. Include language-specific service copy, metadata, contact information and future maintenance in the quote. The multilingual portfolio QA checklist covers publication and navigation checks.

Define what counts as a finished website

A working launch is more than a homepage that looks good on a large monitor. Agree a mobile review, meaningful keyboard navigation, legible image captions, responsive media, a functioning contact journey, basic performance checks, secure editor access and a handover of the published content. Define which devices and browsers will be tested without claiming perfect rendering on every possible combination.

For an existing domain, require a redirect and metadata plan, an indexability check and a submitted sitemap only where access and ownership allow it. Google indexing or search positions cannot be promised merely by shipping code. Record which party is responsible for Search Console verification and follow-up. For enquiry testing, use the contact form delivery checklist.

Make proposals comparable before discussing design

Give every invited provider the same brief and request the same response structure: scope, deliverables, excluded work, content responsibilities, review rounds, milestones, hosting and software costs, usage rights, handover, support and assumptions. A cheap quote may simply exclude the very work another provider priced.

Separate your budget range from the proposed final fee. A realistic range helps a designer suggest an appropriate scope, but the quote should still identify what is included. Use the architecture website cost and scope guide to understand why the content archive, CMS and integrations matter more than a raw page count. Fictional example: a small practice preparing a quote

Fictional illustrative example, not an Atmosferi customer, signed contract or recorded result. Imagine a three-person architecture office replacing a dated website. It serves private homeowners in one region, wants to showcase eight completed projects and needs a way to add new ones without writing code. It has a folder of photographs but still needs to confirm image rights, write concise descriptions and simplify several drawings.

The brief requests a homepage, work index, reusable project template, studio page, services and contact; it labels a journal and second language as optional. The editor must support new project publication. The old project URLs need a redirect map, and the form must create a verifiable enquiry record. The practice provides two sample projects, one preferred launch window and one decision-maker. A designer can now price the identified work rather than guessing from a mood board.

Before the meeting, mark each open decision and its owner. Confirm the next step in writing: a fixed-scope offer, a paid discovery exercise or a request for missing source material. A brief is useful when it reduces uncertainty, not when it pretends the project is already fully specified.
