Architecture website handover and maintenance: what studios should receive.

A website launch is not the end of the project. Use this practical checklist to confirm account ownership, project publishing, forms, backups, SEO monitoring, recovery and realistic maintenance responsibilities.

By Michal Kašpárek · Architect and visualisation specialist25 November 2026

Launch is a milestone. Handover is what makes the website usable next year.

An architecture website can look finished on launch day and still leave the practice exposed. The portfolio loads, the studio likes the typography, and an enquiry form appears to work. Then a team member tries to publish a new project, a billing email goes to a former contractor, or a domain renewal reminder reaches the wrong person. None of those issues are solved by a beautiful homepage screenshot.

A proper handover answers four questions: Who owns the website and its data? Who can change it? How will problems be detected? Who is responsible for fixing them? These questions apply to a five-project sole-practitioner portfolio as much as a multilingual architecture studio with dozens of case studies. The size of the checklist can change; the basic responsibility should not be mysterious.

Do not confuse handover with a promise of permanent support. A one-off design and development contract, a managed website subscription and a separate maintenance retainer are different commercial arrangements. The project owner should know which one was actually agreed, what it includes, and what happens when the arrangement ends.

This guide covers the operational decisions after a website has been built. To define the initial commission, use the architecture website project brief; to decide whether to use a template or tailored system, see the template versus custom guide.

Keep domains, hosting, source files and administrative accounts under clear ownership.

Ask for an inventory of every system involved in publication. At minimum, identify the domain registrar, DNS service, hosting or deployment provider, code repository if applicable, CMS or content store, image storage, analytics tools and the email provider handling enquiries. For each system record the organisation that owns the account, the responsible administrator, the billing contact, renewal terms and how the studio gets access.

The safest default is for the practice to control its domain and business-critical accounts, with appropriately limited access granted to suppliers. A developer can manage deployments without holding the only registrar login. If a domain or platform must temporarily sit under an agency's account, the agreement should explain how ownership and access are transferred later.

Do not put passwords in a public project folder or an email thread labelled “handover”. Use individual accounts, a reputable password manager and multifactor authentication for privileged access. CISA's Cyber Essentials recommends account inventories, least-privilege permissions, MFA and protected backups as foundational measures. Make sure recovery methods also belong to the studio and are not tied solely to a former employee's phone.

Handover inventory · example fields, not actual client accounts
SERVICE: domain / DNS / hosting / source / CMS / images / email ACCOUNT OWNER: [studio legal entity or authorised owner] ADMINISTRATORS: [named roles, access level] BILLING / RENEWAL: [responsible contact and terms] RECOVERY: [securely stored recovery method] EXPORT AVAILABLE: [yes / no / conditions] SUPPLIER ACCESS: [what access, when to review] LAST VERIFIED: [date and reviewer]

Record credentials securely outside this inventory; do not paste recovery codes or secret tokens into website documentation.

Make adding a project a documented task, not a developer-only ritual.

An architecture portfolio has a different publishing workflow from a simple brochure site. The team may need to add a house, arrange a dozen views, include drawings, credit an external photographer, label a proposal as unbuilt and publish a second language. Handover should include a real demonstration using an approved project, not only a tour of the editor interface.

Define the project fields the site expects: title, type, location if permitted, status, year, short description, project narrative, hero image, gallery sequence, drawing captions, collaborators, architecture credits and photography rights. Explain how image crops are chosen for a homepage card versus a detail page. If a component is not editable without code, say so explicitly.

Ask the editor to complete a full test: create a draft, preview it on mobile, change image order, add an alternative text description, correct a collaborator's credit, publish it and then update one fact without breaking the layout. The architecture portfolio CMS selection guide explains why a structured project record matters more than a fashionable product name.

Assign editorial responsibility. Who approves project facts and image rights before publication? Who checks translations? Who can publish live changes? The image attribution and approval checklist helps protect the studio from incorrectly credited work. A capable publishing system should not make it easy to publish confidential work by accident.

Know what is backed up and practise restoring it.

“The provider has backups” is not a sufficient recovery plan. Confirm which assets are included: project texts, CMS database, uploaded media, source code, configuration and deployment settings. Some systems can reconstruct pages from a repository but not recover a deleted media library or manually entered CMS data. Others back up content but not an external file store.

For each data source, record how often it is backed up, where copies live, who may restore them, retention rules and how to recover a specific project. Test at least one restore in a safe environment before declaring the process complete. Review the consequences of restoring a database while keeping newer uploads, form submissions or published URLs. A restore should not accidentally overwrite unrelated recent edits.

Keep a copy outside the platform that could fail or lose access. CERT-EU's guidance recommends a 3-2-1-style backup approach for critical information. The appropriate schedule depends on the site: a studio updating once per quarter has different recovery needs from a live property development website with frequent availability updates.

Separate disaster recovery from normal revision history. Rolling a design change back is not the same as recovering an account, contact form records or original photographs. The handover should state what can be restored and which actions require the original vendor.

Prove that enquiries reach the right person after launch.

A contact page that renders correctly can still fail commercially if email delivery stops, an API key expires or messages are sent to an inbox that nobody monitors. Perform an end-to-end test from the public domain: submit a legitimate enquiry, check server acceptance, confirm delivery to the intended inbox and test the confirmation the visitor receives. Also test invalid entries and mobile error messages without submitting real personal data to a public test system.

Identify the provider handling transactional mail, its billing owner, domain authentication where applicable, message retention and a recipient responsible for checking delivery errors. Distinguish client notifications from internal diagnostic emails. Flooding a studio owner's personal inbox with every automated status alert can hide the real enquiry, which is an impressive way for a website to sabotage its own purpose.

Document alternative contact routes. If the form is unavailable, is there a visible business email address? Does a booking link still point to the right calendar and meeting method? Does the site clearly explain what happens when someone submits a brief? Use the architecture studio contact-form QA guide for repeatable tests and failure scenarios.

Make the owner of the enquiry process explicit. The developer can maintain a technically working form, but the practice still needs someone to respond to messages and keep the recipient address current.

Hand over search monitoring, not just SEO metadata.

A launch report should distinguish what was configured from what has actually been discovered and indexed. The studio needs access to its Google Search Console property, a known sitemap URL, verified canonical pages and a list of important project and service URLs. Explain which metrics are available and who checks coverage, broken links and changed redirects after future updates.

Google Search Central's maintenance guidance recommends regular technical review. After a domain or URL change, Google's site-move guidance covers URL mapping, redirects and Search Console verification. Submitting a sitemap helps discovery, but it does not guarantee indexing or a ranking. A report should never call a deployment “indexed by Google” merely because a sitemap generator passed a build test.

Record what to do when a new project is published: confirm its public URL, canonical, meta description, main heading, image context, internal link from the projects page and inclusion in the sitemap where appropriate. If a project is confidential or no longer public, the editorial and technical rules are different; do not silently add every draft to an indexable sitemap.

For a redesigned studio portfolio, preserve known incoming project links whenever possible. The architecture portfolio URL migration checklist covers redirects and content ownership in more detail. Search monitoring is a recurring operational duty, not a one-time green badge at launch.

Agree how design, software and content changes reach production.

Write down who can publish a CMS edit, who can merge a code change and who is authorised to create a production deployment. Define a basic review path: preview the change, test the affected page type, check contact and navigation functions if relevant, deploy, and verify the actual public URL. A successful repository build alone does not prove that a hosting provider has served the intended release.

Set an update routine suited to the website's components. For a maintained platform, this may include dependency and security updates, API credentials, extension licences, uptime checks and periodic accessibility reviews. A mostly static site may need little runtime maintenance but still requires domain renewals, content editing, link checks and ownership of its hosting account.

Give changes a rollback or recovery procedure. When a major update breaks a project gallery, the operator should know whether to revert code, restore a content version, or disable a problematic feature. Avoid putting sensitive API keys into public repositories or source bundles. Keep production, preview and test environments clearly distinguished.

If a new architectural film, interactive 360° viewer or heavy image gallery is added, include a mobile performance review in the publication process. See the portfolio performance checklist for practical LCP, INP and layout-stability tests. Ongoing updates should protect the studio's presentation, not gradually undo it.

Separate one-time handover from an ongoing support agreement.

A transparent website proposal should say what is included at launch and what begins later. Content entry, code improvements, new project layouts, hosting fees, security maintenance, platform licences, backups, analytics reporting and technical support are distinct items. “Maintenance included” is too vague unless the actual activities, response process and limitations are written down.

Ask for clarity about response times, exclusions, billing frequency, support channel and what happens when a contract ends. Architecture studio website handover and first-month checklist.

  • The practice knows who owns the domain, DNS, hosting, CMS and source repository.
  • Named administrators have individual access, appropriate permissions and MFA.
  • Billing contacts, renewal terms and recovery routes are documented securely.
  • A studio editor can publish and correct one real project without developer intervention where agreed.
  • Project texts, image originals, licences, credits and multilingual data have a documented export path.
  • Backups cover the necessary data sources and a safe restore has been tested.
  • The public contact form, notification email and alternative contact route work end to end.
  • Google Search Console ownership, sitemap and important project URLs are confirmed.
  • Old portfolio addresses have working redirects where they changed.
  • A production release can be verified, and a broken release has a recovery process.
  • New images, videos and interactive media receive a mobile and accessibility review.
  • One person owns operational checks, even if an external supplier performs them.
  • Ongoing services, fees, exclusions, response arrangements and exit conditions are explicit.
  • A follow-up review is scheduled after enough real visitors and editorial activity to find issues.

A strong handover is not glamorous, but it is part of good web design. It lets an architecture practice focus on projects rather than wondering who can repair the contact form or recover a lost portfolio. The website should remain a working asset after the launch presentation is over.
